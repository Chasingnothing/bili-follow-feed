## 1. 项目形态

### 为什么是用户脚本，而不是网页或 App

因为这个工具**必须住在 `www.bilibili.com` 这个源里**。

关注列表和动态流的接口要求登录态。而这个项目的一条硬约束是**不落地任何凭据**。
两者能同时成立，靠的是一个巧合：脚本跑在 `bilibili.com` 源内，
于是 `fetch` 到 `api.bilibili.com` 时**浏览器自动带上了用户的 SESSDATA** —— 我们一行登录代码都不用写。

**一旦离开这个源，这条路就断了。** 而且不是配置 CORS 能解决的：

> 跨源**带凭据**的请求，要求服务端返回 `Access-Control-Allow-Origin: <确切源>`
> **且** `Access-Control-Allow-Credentials: true`。而 `ACAO: *` 与"带凭据"在规范上互斥。

B 站的接口是给站内页面用的，不会为第三方源这么做。这一点有直接证据：
`feed/all` **匿名访问返回 `-101 账号未登录`** —— 也就是说"跨源但不带凭据"这条路是死的。

这就是为什么没有 PWA、没有网页版、也没有后端：**用户脚本是唯一能不写登录流程又不碰凭据的形态。**

### 为什么入口是一个 404 页

入口是 `https://www.bilibili.com/agent-feed`，脚本的 `@match` 收窄到这一个路径。

2026-09-11 实测：B 站对未知路径**不重定向、不改写 URL**，只在原址渲染它的 404 页。
我们**接管的就是那个 404 页**。收窄 `@match` 的好处是其他 B 站页面**完全不加载**这个脚本。

**历史上踩过**：早期版本用 hash（`#/my-feed`），`@match` 是全站，导致每个 B 站页面都要解析
两百多 KB 的脚本。而且旧版靠 `hashchange` 判断"用户是否离开"，**B 站有权改写 hash** ——
一旦它这么做，脚本就会静默把页面还回去。迁到独立路径后该逻辑整个删掉了。

### 两种模式

| 模式 | 数据来源 | 解决什么 |
|---|---|---|
| **模式 1 · 动态流** | 全局动态流 `feed/all`，按时间窗翻页 | 想一次看完所有关注的人的更新 |
| **模式 2 · UP 主拉取** | 逐个 UP 拉 `feed/space`，每个留最新 5 条 | 关注的人太多，全局动态流翻不到底 |

## 3. 关键设计决策

### ① 接管页面：隐藏原生 body

`html.bff-active body { display: none }`，挂载点挂在 `document.documentElement` 下
（因为 `@run-at document-start` 时 `document.body` 还不存在）。

**副作用**：B 站 404 页上的导航也被隐藏了，所以工具栏必须自带一个「返回 B站」的出口。

### ② 三个 B 站字段陷阱

2026-09 实测，这三条**全部是"先跑探针"抓出来的**，光看设计文档发现不了：

| 假设 | 真实 |
|---|---|
| `stat.play` 是 number | **是字符串** `'59'`，而且带单位的会写成 `'3.4万'` |
| `cover` 是 https | **是 `http://`** → HTTPS 页面按**混合内容**拦截，表现为一屏碎图 |
| 时间在 `archive.pubdate` | **该字段不存在**，时间在 `module_author.pub_ts`，且是**字符串、秒级** |

### ③ `<a>` 不能嵌 `<a>`，`<button>` 不能放进 `<a>`

卡片外层是 `<div>`，里面是两个**并列**的 `<a>`（内容 / UP 主页），「⋯」按钮也是并列的兄弟节点。

`<a>` 嵌 `<a>` 是非法 HTML，浏览器会**静默拆掉内层**；带 `href` 的 `<a>` 也不允许包含交互内容。
**同一个坑踩了两遍**（卡片重构一次、加「⋯」一次）。板块标题同理，所以它是 `<div>` 不是 `<button>`
（里面要放拖动柄和 ↑/↓ 按钮，按钮套按钮是同一类问题）。

### ④ 分组与 B 站**隔离**，但按名字复用

本地 `membership` 是唯一事实来源，B 站的改动不会自动流入。但 `Group.biliTagId` 是**显式映射** ——
不能靠 id 前缀（`bili-`）猜，因为用户先在本地建的同名分组 id 是 `local-N`，永远匹配不上。

**实测踩过**：用户在本地建「娱乐」，之后在 B 站也建「娱乐」并加人。补充导入时因 id 前缀不同
被判定成"本地没有" → **新建了同名分组，UP 全进了新组**。
修法：导入时按 **① 已有 tagid → ② 同名 → ③ 新建** 的顺序匹配。

**配套约束（更隐蔽）**：翻译 B 站归属时**必须查映射表，不能拼 `bili-<tagid>`** ——
复用同名分组后它的 id 是 `local-N`，拼出来的 id 指向不存在的分组 → **脏引用 → UP 静默掉进未分类**。

### ⑤ 分歧检测必须用快照

「B 站那边给某个 UP 换了分组」不会自动跟随（这是隔离的设计意图），但**分歧是静默的** ——
用户会以为程序坏了。所以存一个 `bff:biliSnapshot`。

**直接拿"B 站当前值"和本地 membership 比是错的** —— 那会把**所有用户手动改过的 UP
都误标成"B 站变了"**。必须和"上次看到过的 B 站值"比。

### ⑥ 隐藏分组必须与其他分组**互斥**

`HIDDEN_ID` 只把内容从页面滤掉，**不取关**。

互斥不是风格选择：如果一个"隐藏"的 UP 同时留在某个真实分组里，他的内容**仍会在那个板块渲染** ——
功能看起来就是坏的。所以加入真实分组会清掉 hidden，加入 hidden 会替换整个 membership。

主区不渲染「隐藏」板块（它永远是空的），只在侧边栏和批量面板里作为管理入口。
工具栏计数显示「已隐藏 N 条」，让消失的内容有可见解释。

### ⑦ 系统分组要"自愈"

**踩过的 bug**：新增了「隐藏」系统分组，但**老用户三处都看不到**。

**原因**：`loadGroups()` 在存储非空时直接返回旧列表，而 `systemGroups()` 只在存储为空时才生效 → **"新增一个系统分组"这种纯追加式升级传导不到已安装用户**。

**修法**：`loadGroups()` 里补齐缺失的系统分组并落盘。**放在读取路径上，任何调用方都不可能忘记它**
（放在某个 init 函数里就还会被忘）。

### ⑧ 增量刷新：撞见已知条目就停

早期版本"每次刷新都要重拉"。两个成因：缓存的有效期太短（当时是 10 分钟；**现在是 10 秒**，
见 §3⑬）；而且命中缓存只是"跳过拉取"，
**丢了尾部游标** → 第一次「加载更多」又从第 1 页重来。

**修法**：命中缓存**先渲染**，再**从顶部往下抓、撞见已知 id 就停**（动态流是倒序的）。

**关键安全边界**：追满页数上限仍未撞见已知条目 → `caughtUp: false` → **退回完整加载**，
绝不把两段拼接（那样会静默丢一段）。

### ⑨ 模式 2 的板块组装**方向相反**，不能复用模式 1 的

| | 模式 1 | 模式 2 |
|---|---|---|
| 起点 | 一堆**条目**（全局动态流） | 每个板块的 **UP 列表** |
| 动作 | 按 UP 的归属把条目**分**到各板块 | 按 UP 列表去缓存里**取**条目 |

所以模式 2 的板块里可以出现"有 UP 但一条都没有"的情况（刚进页面就是这样），
文案也不同（「还没有拉取这个板块的内容」vs「这个分组最近没有更新」）。

**模式 2 不产出「未分类」和「隐藏」板块** —— 这是它的设计前提。
实测样本里 **93% 的关注都在 B 站默认分组**（即未分类），模式 2 的卖点是"按 UP 逐个看"，
而那几百个恰恰是没被整理过的，逐个拉既慢又没意义。

### ⑩ 「层数」和「每个 UP 保留条数」是同一个数字

```ts
export const MAX_LAYER = MAX_PER_UP;   // 都是 5
```

这是刻意的对齐，带来一个不明显的推论：**被淘汰的 UP 重新拉取后会立刻显示满 5 条**。
因为 `items.slice(0, layer)` 取满缓存里全部 5 条，而且被淘汰的 UP **不会**被"新鲜度"检查跳过
（那个表是由**现存**缓存条目构建的，被淘汰就查不到 → 视为不新鲜 → 照常重拉）。

层数只是**过滤条件**，然后整体统一排序 —— 所以不存在"层与层之间怎么排"的问题。

### ⑪ 「空结果」要记，"出错"**绝不能记**

模式 2 靠"上次拉取时间"决定一个 UP 要不要重拉。两种"没拿到东西"必须区别对待：

| 情况 | 记吗 | 为什么 |
|---|---|---|
| 拉到了条目 | 记 | 正常 |
| **拉成功但一条可显示的都没有**（全是转发 / 直播推广位） | **记**（存空数组） | 不记 → 永远"不新鲜" → **每次点拉取都重拉这几个请求，永远** |
| **请求出错** | **不记** | 记了就把"网络抖动"永久固化成"这个 UP 没内容"，用户再也没机会拿到 |

配套：界面要**分开报**「查过的」和「有内容的」，否则用户永远看不懂计数器为什么到不了满分。

### ⑫ 模式 2 的「层数」**刻意不落盘**

**判据：重置的代价是零，持久化的代价是困惑。**

「多看一条」是**只读缓存、不发任何请求**的。所以刷新后回到第一层，用户损失的只是"再点一下" ——
不重发请求、不丢数据（缓存里那 5 条还在）。

而它一旦落盘，就会**跨会话悄悄累积**：层数按板块分别记，用户每次在某个板块点过「多看一条」，
那个板块就被永久记住，过一阵子回头看就成了"各个板块都停在第二层"，**界面上没有任何提示**。

> 一个有用的旁证：它旁边那个"每板块页码"**从来就没落过盘**。
> 同一个文件里两种状态处理方式不一致，说明层数持久化更像遗漏，不像设计。

**排查时的一个坑**：这个问题的现象容易被归因到错误的按钮上 ——
「拉取更多」（扩大 UP 覆盖，发请求）和「多看一条」（加深层数，**不发请求**）是两个按钮。
代码里唯一能改层数的是后者。
**凡是"现象描述的因果"和"代码里的因果"对不上时，先确认再说**，否则会去修一个不存在的问题。

### ⑬ 两条「刷新」路径**不等价**，而且缓存命中那条曾静默失败

| | 界面「刷新」按钮 | 浏览器 F5 |
|---|---|---|
| 入口 | `load(h, **force=true**)` | `load(h, **force=false**)` |
| 行为 | **完整加载**：清空重建，从第 1 页重拉，一直翻到窗口边界 | 缓存命中 → **增量刷新**：从顶部往下抓，撞见已知条目就停 |

**用户的心智模型是"点刷新就该检查更新"，所以这两条路应该都能检查。** 但缓存那条曾经会静默失败：

`incremental` 里写的是 `try/finally`，**没有 `catch`**：

```ts
let res;
try {
  res = await fetchNewer({ ... });
} finally {
  setRefreshing(false);     // ← 只有 finally
}
```

增量请求一旦抛错（最典型的是 B 站风控返回 `-412 请求被拦截`），异常会一路穿出 `load`，
而调用处是 `void load(...)` —— 于是它变成一个**未处理的 promise rejection**，
`setError` 永远不会被调用。

**症状**：一份过期的缓存 + **毫无提示**。用户报的是"刷新页面不检查最新更新"，
真相是**检查了、失败了、没说话**。

**而且故障会自我延续**：失败时不会落盘，`cached.at` 保持旧值，所以每次刷新都重试、
每次都静默失败。

> 这与 §3⑪ 的「空结果 vs 没查过」是**同一类问题**，只是那次在**写**路径上，这次在**读**路径上。
> 教训：**"静默失败"不只发生在写操作上。凡是"我做了但失败了"的地方，都要能说出来。**

**顺带修的**：防抖从 **60 秒降到 10 秒**。原来那个 60 秒正好挡住正常操作 ——
打开页面（检查一次并落盘）→ 没看到新内容 → 按 F5 想再确认一次 → **落在防抖里，一个请求都不发**。
`fetchNewer` 撞见已知条目就停，一次检查通常**只有 1 个请求**，
真正值得防的只是"手抖连按两次刷新"。

### ⑭ 缩窗口筛出空时，要先去**确认**再下结论

时间窗是【显示】范围，缩窗口**不发请求**（这是 v0.8.4 的优化）。但这带来一个陷阱：

> `cardsRef` 里最新的那条**未必真的就是最新的** —— 缓存可能是旧的
>（比如 ⑬ 那个静默失败让缓存一直没跟上）。

于是"缩到 1 天"会把一份陈旧的缓存筛成空数组，界面上是一片空白。
**用户看到的是"没有视频"，真相是"缓存没跟上"。**

**修法**：筛出空时，先花 **1 个请求**去顶部确认一次 —— 真有更新的就补进来；
确实没有，界面再明确显示「此时间窗内没有内容」，而不是一片空白。

> 教训：**凡是"根据本地状态推断远程状态"的地方，本地状态不可信时都要能复查一次。**
> 以及：**空结果必须说话。** 一片空白让人无法区分"确实没有"和"出问题了"。

## 4. 实测结论：B 站接口

### 接口与签名

| 接口 | 需要 WBI 签名 | 备注 |
|---|---|---|
| `x/web-interface/nav` | 不需要 | 取自己 mid |
| `x/relation/tags` / `x/relation/followings` | 不需要（需登录） | 关注列表登录可看自己全部 |
| `x/polymer/web-dynamic/v1/feed/all` | **不需要** | 全局动态流。一页 20 条 |
| `x/polymer/web-dynamic/v1/feed/space` | **不需要** | ⭐ **单个 UP 的动态流**。一页 12 条 |
| `x/space/wbi/arc/search` | **需要 WBI** | 缺 `w_rid`/`wts` 直接 412。**但已经不需要它了** |

**`feed/space` 是本项目最重要的发现之一**：它让"逐个 UP 拉最新"**不需要实现 WBI + MD5**
（浏览器的 WebCrypto 故意不提供 MD5）。而且它的 item 结构与 `feed/all` **完全一致**，
所以映射函数原样复用。

### `offset` 是**键值游标**，不是位置序号

| 项 | 实测值 |
|---|---|
| 形态 | `1247495679462342665` —— 19 位纯数字 |
| 与最后一条的关系 | **完全等于**该条的 `id_str` |
| 同一个 offset 请求两次 | 结果完全一致（服务端锚定稳定） |
| `has_more: false` 时 | 返回空串 `""` |

> ⚠️ **差点误判**：19 位纯数字很容易被当成"页码/序号"，然后得出**完全相反**的结论。
> 决定性判据是**与已知量对照**：它恰好等于本页最后一条的 `id_str`。
>
> ⚠️ 它**超过 `Number.MAX_SAFE_INTEGER`** —— 必须全程当字符串，**永远不要 `Number()`**。

**由此解开三件事**：① 顶部插入新内容不会让游标错位（语义是"比这个 id 更旧的那些"）；
② 截断缓存后游标可以安全恢复；③ 增量刷新可以从"id 集合"升级为"数值比较"。

**修法：按页记 checkpoint，截断时取可用的最后一个。**

```ts
// 翻页时
checkpoints.push({ count: 已收集的条目数, offset: page.nextOffset });

// 落盘时
const cp = checkpoints.filter(c => c.count <= MAX_CACHED).pop();
tailOffset: cp?.offset ?? null;
```

**关键细节**：offset 对应本页最后一条**原始**条目，而原始条目含图文/转发/直播（会被过滤掉），
所以**不能**用"最后一张卡片的 id"来推，**必须按页记**。

### 动态内容类型

顶层 `type` 与 `major.type` 的组合（`feed/all` 与 `feed/space` 一致）：

| 顶层 `type` | `major.type` | 内容在哪 | 处理 |
|---|---|---|---|
| `DYNAMIC_TYPE_AV` | `MAJOR_TYPE_ARCHIVE` | `major.archive` | ✅ 视频 |
| `DYNAMIC_TYPE_DRAW` | **`MAJOR_TYPE_OPUS`** | `major.opus` | ✅ 图文 |
| `DYNAMIC_TYPE_FORWARD` | `null` | **`orig`**（被转发的原帖） | 过滤 |
| `DYNAMIC_TYPE_LIVE_RCMD` | `MAJOR_TYPE_LIVE_RCMD` | — | 过滤（**B 站插的推广位**） |

> **图文走 opus，不是 `draw`** —— 因为请求里带了 `features: itemOpusStyle`。
> `major.draw` 是旧格式，**我们拿不到**；照它写就是白写。

**图文字段路径**（`modules.module_dynamic.major.opus`）：

| 要的 | 取哪 | 坑 |
|---|---|---|
| id | `id_str` | 与 offset 同一 id 空间，19 位字符串 |
| 链接 | `opus.jump_url` | ⚠️ **协议相对**（`//www.bilibili.com/opus/<id>`），要补 `https:` |
| 正文 | `opus.summary.text` | 够用 —— emoji 已是 `[名字]` 纯文本 |
| 标题 | `opus.title` | ⚠️ **常为空串**，不能当正文 |
| 封面 | `opus.pics[0].url` | ⚠️ **是 `http://`**；`pics` 可能为**空**（纯文字） |
| 统计 | `module_stat.like/comment/forward.count` | 图文**没有播放量** |

**转发的两个事实**：① 转发自己的 `major` 是 `null`，内容全在 `orig`；
② `orig.modules.module_author.following` 实测为 **`false`** ——
**转发确实会把你没关注的人带进来**，这正是保持过滤的理由。
（样本：某 UP 的一页 12 条里 **11 条是转发**，过滤后只剩 1 条。）

### ⚠️ `stat` 是**给人看的**带单位字符串

实测 `"play": "3.4万"`、`"danmaku": "112"`。
`Number("3.4万")` → `NaN` → 兜底成 0 → **所有播放量上万的视频显示 0 播放**，排序也失效。

修法是专用的 `parseStatCount`，**保证永远返回数字，绝不返回 `NaN`**。

> **这个 bug 测试没抓到，因为 fixture 里恰好是 `"99"`（不带单位）。**
> **fixture 太干净会掩盖真实数据的分支** —— 所以本项目的 fixture 全部取自真实响应。

## 5. 数据与存储

**全部在 `localStorage`，属于 `www.bilibili.com` 这个域**。脚本每次刷新都是全新的，
"记忆"完全靠读写 localStorage。

| 键 | 内容 | 增长特性 |
|---|---|---|
| `bff:feedCache` | 模式 1 的卡片 + 窗口 + 尾部游标 + checkpoints | 封顶 600 条 |
| `bff:up:<mid>` | 模式 2：**一个 UP 一个键**，`{at, lastUsedAt, cards[]}` | 每 UP ≤ 5 条，最多 600 个 UP |
| `bff:followingsCache` | 关注列表（裁剪后）+ B 站分组 | 随关注数 |
| `bff:groups` / `bff:membership` / `bff:biliSnapshot` | 本地分组 / 归属 / 分歧快照 | 取关后**刻意保留** |
| `bff:readVideos` | 已读 id | **封顶 3000** |
| `bff:mode` / `bff:collapsedGroups` / `bff:collapsedSections` / `bff:lastVisitAt` / `bff:loadMorePos` | 界面状态 | 小 |

### 体积实测

> ⚠️ **单位陷阱**：`JSON.stringify(s).length` 数的是 **UTF-16 单元**，
> 而 localStorage 按 **2 字节/单元** 计费。把"单元数"当"字节数"会让结果**正好差一倍**。

**Chrome 的配额是 10 MiB**（`kPerStorageAreaQuota = 10 * 1024 * 1024`
= 5,242,880 单元），另有 100 KB 宽限。

实测卡片平均 **423 UTF-16 单元 = 847 字节**（图文帖比视频帖小，它没有时长和播放量）。

| 键 | 最坏情况 | 单元 | 占 Chrome 10 MiB |
|---|---|---|---|
| `bff:up:*` | 600 UP × 5 张 | 1,192,200 | **22.7%** |
| `bff:feedCache` | 600 张 + 50 checkpoints | 274,108 | 5.2% |
| `bff:followingsCache` | 283 UP | 42,245 | 0.8% |
| `bff:readVideos` | 3000 条 | 45,000 | 0.9% |
| **合计** | | 1,553,553 | **≈29.6%** |

**结论：Chrome 上余量充足。**

1. **Firefox / Safari 的配额明显更小**（Firefox 是 5 MiB 量级）。
   2.96 MiB 在 5 MiB 下占 **59%** —— 能活但更紧。
2. **"卡片瘦身"只省了 17%，不是 44%**。因为 `slimItem` **只去掉 `upMid` 和 `url`**，
   故意**保留 `upName` / `upFace`** —— 用户取关过的 UP 不在 UP 索引里，去掉名字就再也显示不出来了。
   按 `mid` 作 key 去重 `upMid`、按 `id` 拼 `url` 是安全的；名字和头像不是。

**写入失败会返回 `false`**，界面出提示 —— 不静默吞掉（否则配额满时已读状态会悄悄停止保存）。

### 淘汰策略

`bff:up:*` 满 600 个时按 **`lastUsedAt` 最旧的先淘汰**，保证"正在看的板块不会被先淘汰"。
所以「多看一条」会顺手刷新该板块所有 UP 的使用时间。

**一个性能细节**：`saveUpItems` **只在"真的要新增一个 UP 且已达上限"时才算淘汰**。
淘汰要逐个 `JSON.parse` 全部条目，每次保存都调会让拉 N 个 UP 的开销变成
**O(N × 已缓存数)**（600 已缓存 + 拉 500 个 = 30 万次解析）。只扫 key 名的函数足够应付其余情况。

## 6. Bug 类别学（这部分最值钱）

| 类别 | 实例 | 教训 |
|---|---|---|
| **非法嵌套** | `<a>` 嵌 `<a>`、`<button>` 放进 `<a>`、按钮套按钮 | 浏览器会**静默拆掉内层**，表现为"点了没反应"，不是报错 |
| **图层遮挡** | 落点提示用 `inset box-shadow` 画在"背景层"，被不透明的标题子元素盖住 | CSS 绘制顺序：**元素背景（含 inset 阴影）→ 子元素**。要盖住子元素得用伪元素或提高层级的实际元素 |
| **硬编码偏移量** | 浮层定位 `innerHeight - 60`（实际菜单 390px） | 别拍数字。**测量后再定位**（`useLayoutEffect` 在绘制前） |
| **只在全新安装生效的初始化** | 新增的系统分组传导不到老用户 | **"只在存储为空时初始化"的代码没有升级路径。** 凡是新增默认项，都要想清楚已装用户怎么拿到 |
| **类型说谎** | 一个类型复用了错的形状；effect cleanup 返回了 `boolean` | 运行时测试**抓不到**，只有 `tsc` 能抓 → 测试命令必须带类型检查 |
| **静默失败** | 配额满时 `catch {}` 吞掉异常 → 已读状态停止保存而用户不知 | 写操作要**上报结果** |
| **静默失败（读路径）** | 增量刷新只有 `try/finally` 没有 `catch`，接口报错（如风控 `-412`）变成未处理的 rejection → 用户看到一份过期缓存且**毫无提示**，以为自己"点了刷新没反应" | **"静默失败"不只发生在写操作上。** 凡是"我做了但失败了"的地方都要能说出来。错误的形状是 `try/finally` 少了 `catch`，diff 里很难看出来 |
| **空结果不说话** | 缩窗口筛出 0 条 → 一片空白。用户无法区分"这个窗口确实没内容"和"缓存旧了/出问题了" | **空结果必须给文案。** 而且"根据本地状态推断远程状态"的地方，本地不可信时要能复查一次（这里花 1 个请求去确认） |
| **断言写反了却不自知** | 修"切窗口白屏"时，我先猜"空列表会翻满 40 页形成请求风暴" —— 实测**只有 2 个请求**，`fillToCutoff` 用 `oldestPubTs === 0` 判定到头 | 猜测要用测试打脸。这次是测试否掉了我的假设，而不是我"想通了" |
| **无上限增长** | 已读集合每点一个视频加一条、永不清理 | 主动封顶。**churn 型的增长通常不是问题，单调递增的才是** |
| **脏引用被容错掩盖** | 拼错的分组 id 被当成"未分类"兜底 → UP 静默消失 | 容错是好的，但**要保证不产生脏引用**，不能靠兜底 |
| **展示字符串被当数字** | `stat.play` 是 `"3.4万"`，`Number()` → `NaN` → 兜底成 0 → 上万播放全显示 0 | 接口字段有**两种数字**：机器读的和给人看的。判据是"有没有单位后缀"。⚠️ **fixture 太干净会掩盖这个分支** |
| **"空结果"与"没查过"混为一谈** | 某 UP 全是转发 → 一条都存不下 → 永远"不新鲜" → **每次拉取都重拉他** | 存储层里**"空数组"和"没有这个键"必须是两种状态** |
| **失败被误记成成功** | 与上一条成对：出错时若记"查过了"，一次网络抖动会被永久固化成"这个 UP 没内容" | 记录"已完成"时要区分**成功且为空**（记）和**失败**（不记）。错误必须可重试 |
| **共享按钮抢 handler** | 「拉取更多」兼作「暂停」，但批量拉取里没有任何地方去设那个暂停标志 → **有续跑路径、没有暂停入口** | **"有恢复路径"不等于"有暂停路径"**，两条路要分别验证 |
| **反馈放错位置** | 拉取结果提示条固定在页面顶部，而用户正盯着页面下方的板块 → 完全看不到 | 反馈要**贴着触发它的对象**放。"我测试时看到了"不等于"用户会看到" |
| **只看表面特征就下结论** | 19 位纯数字的 `offset` 看起来就是页码/序号，差点据此判定"会漏内容" | 表面特征 ≠ 语义。决定性判据是**与已知量对照**（它恰好等于最后一条的 `id_str`）。**能对照就别猜** |
| **单位混淆** | 把 UTF-16 单元数当成字节数写进文档，体积**差一倍**；又用了错的配额（5 MiB vs 实际的 10 MiB） | 凡是体积/配额数字，**必须写明单位**并核对**权威出处**。**数字自相矛盾时先怀疑自己** |
| **热路径里的"以防万一"要标价** | 每次保存都为了"可能越界"而解析全部缓存 → 拉 N 个 UP 变成 O(N × 已缓存数) | 判据是"这个昂贵分支真的会走到吗" |
| **写文档时没核对系统时间** | 文档里盖了一整批错日期 | 凡是写进文档的事实都要复核 —— **包括日期** |

### 一条反复奏效的流程

> **动手前先跑探针，量过再写代码。**

这条流程抓到了三个字段陷阱、省掉了整套 WBI/MD5、发现了 `feed/space` 这扇免费的门。
**所有"我以为"最后都被实测修正过。**

## 7. 已知限制与规模化硬墙

### 限制

| 限制 | 说明 |
|---|---|
| **没有历史库** | 只显示动态流窗口内的内容。两周没打开，那两周就看不到了 |
| **不能定时抓取** | 用户脚本只在页面打开时存在，架构上做不到 |
| **状态困在一个域** | 全部状态在 `bilibili.com` 的 localStorage 里 |
| **和 B 站红点是两套** | 因为从不写 B 站 |
| **跨平台需要重构** | 约 70% 代码平台无关，但 `bvid`/`upMid`/`url` 写死了 B 站概念 |

### 关注数很大时的硬墙

| 墙 | 现状 | 后果 |
|---|---|---|
| **关注列表最多导入 5000 人** | `ps=50` × `MAX_PAGES=100` | 超出会被截断，但**会显示提示**（不再是静默丢弃） |
| **侧边栏无虚拟化** | 直接 `map()`，搜索时封顶 50 行 | 几千个关注 → 几千个 DOM 行。折叠 + 搜索上限只是缓解，真正解法是虚拟列表 |
| **模式 2 的请求数 = 该板块的 UP 数** | 每个 UP 最多 3 个请求 | 几百 UP 的板块 = 上千请求。已有护栏（每 20 个停 2 秒、同一时刻只拉一个板块、可暂停），**但仍可能触发风控** |
| **缓存只覆盖最近用过的 600 个 UP** | 超出按最久未用淘汰 | **缓存里没有 ≠ 没有更新。界面绝不能据此下"无更新"结论** |

## 8. 未来方向

- **手机端**：Tampermonkey 现在官方支持 Android（Firefox / Edge）与 iOS Safari，
  同一份产物可以直接装。**唯一要补的是手机断点** —— 侧边栏固定 260px 且不收缩，
  在 390px 宽的手机上会占掉 67% 屏幕。⚠️ iOS Safari 有「7 天无交互清空脚本可写存储」的策略，
  而这整个应用的"记忆"就是 localStorage，**未在真机确认过**。
- **跨平台**（抖音等）：技术上可行，但障碍是**认证 + 签名**，不是跨域
  （最难的是产品问题：同一个人在 B 站和抖音是不同账号，"统一的我关注的人"做不到）。
  注意这与手机端**不是同一堵墙**：跨平台卡在签名，手机端卡在同源/cookie。
- **架构泛化**：把 `platform + contentId + creatorId(字符串)` 替换掉
  `bvid + upMid(number) + url`。不做的话将来加平台会更痛（且需要一次存储迁移）。
- **本地历史累积**：零请求成本，能覆盖大部分"想要无限历史"的实际需求。

### 可维护性欠债

- `App.tsx` 偏大，该拆 hooks（模式状态、拉取编排、两套板块渲染都挤在里面）
- `bff:schemaVersion` 机制写了但从未接上 —— 追加式变更用"自愈"更稳，但**破坏性变更会真的需要它**
- CSS 集中在一个文件里，可拆
- `useFollowings` 测试覆盖偏薄
- 图文多图预览没做（现在只显示第一张 + 图片数量角标）
- 缓存上限 600 没有界面提示（超过后计数器永远到不了满分，用户无从得知原因）
