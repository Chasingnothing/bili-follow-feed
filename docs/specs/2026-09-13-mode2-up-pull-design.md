## 1. 模式 1 的改动

### 1.1 暂停 / 继续

`fillToCutoff` 增加中断判据（纯函数，可测）：

```ts
export interface FillOptions {
  // ...现有字段
  /** 每页开始前询问是否应中断 */
  shouldStop?: () => boolean;
}
// FillResult['stoppedBy'] 增加 'paused'
```

- 中断发生在**页边界**：当前请求会跑完，最多多等一次延迟（400ms）+ 一次往返
- 按钮点下**立即**变「暂停中…」，避免"点了没反应"
- 暂停后：`covered=false`、新增 `paused=true`，界面显示"已暂停 · 已完成 N 页"
- 「继续」→ 用 `tailOffset.current` 重新进入 `fillToCutoff`
- **绝不丢已拉到的内容**

同一个 `shouldStop` 机制贯穿三个长任务：`fillToCutoff`、`loadMore`、`fetchHistoryForUps`（模式 2）。

### 1.2 ⭐ 渲染优化 —— 这才是"卡死"的根因

**证据**：项目里**没有任何 `React.memo`**；`Sidebar.tsx:159` 是 `items.map(...)` 无限长渲染；
而 `App.tsx:470-488` 的 Sidebar props **没有一个来自 `cards`**。

所以加载期间（`MAX_FILL_PAGES = 40`，每页一次 `setCards` + 一次 `setFilledPages`）：
App 重渲染 → Sidebar 无谓地重渲染**全部 UP 行** ×最多 40 次。
关注 5000 人 = 5000 行 × 40 次。**这就是卡死。**

**修法（三处，都很小）**：

| 改动 | 位置 | 作用 |
|---|---|---|
| ① `onOpenGroupMenu` 包成 `useCallback` | `App.tsx:487` | 现在它是内联箭头，**会让 ② 完全失效** |
| ② `Sidebar` 套 `React.memo` | `Sidebar.tsx` | props 全不依赖 `cards` → 加载期间**完全不重渲染** |
| ③ `setCards` 节流（累计 ~400ms 才刷新一次画面） | `useFeed.ts` | 40 次渲染 → 几次；`setFilledPages` 同理合并 |

**优先级：高于暂停按钮。** 暂停只能让用户主动停，但已经渲染出来的行还在，
之后任何一次 `setCards` 仍会重渲它们。①②③ 才是根治。

> 附带发现：`Sidebar.tsx:95` 的 `isCollapsed` 在**有搜索词时强制展开所有分组**
> （`q ? false : collapsed.has(id)`）→ 搜索时会渲染全部匹配的 UP 行。同一个问题的另一个入口。

### 1.3 游标 checkpoint（既有 bug，独立）

见 `HANDOFF.md` §5⑬：翻页时记 `{ count, offset }`，截断时取 `count <= 600` 的最后一个 offset，
游标不再置 `null`。消除"越过 600 条后每次刷新都要从第 1 页重走"。

### 1.4 关注列表 2000 上限（既有 bug，独立）

- `MAX_PAGES` 40 → 120（`ps` 硬顶 50，`pn` 未观察到上限）
- **终止条件从"短页"改为 `total`** —— "短页"在服务端静默截断时会失效
- `total` 每页都有，**无需额外请求**；用它比对，拉不全时**明确提示**
- `relation.ts` 的 `fetchFollowingsTotal()` 可删（第一页响应里本来就有 `total`）

## 2. 模式 2 的组装方式

**关键：模式 2 需要自己的板块组装逻辑**，不能复用 `buildSections`。

| | 模式 1 | 模式 2 |
|---|---|---|
| 输入 | 动态流卡片 | 该板块的 UP 列表 + 缓存 |
| 方向 | 卡片 → 按 UP 归属分板块 | **UP → 取其缓存视频** |
| 空板块 | 仍生成空 Section | 板块的 UP 可能**一条缓存都没有** |

```
板块的 UP 列表  ←  复用侧边栏 byGroup 的同一套 membership 映射
        ↓
每个 UP 取"最近 N 条"（N = 该板块的层数，1..5）
        ↓
汇总 → 按发布时间倒序（沿用工具条排序）→ 分页 20/页
```

**层数的含义就是"每个 UP 最多贡献几条"** —— 所以不存在"层与层之间怎么排"的问题，
它只是一个过滤条件，排序始终统一。

## 4. 「拉取更多」

- **目标**：该板块全部 M 个 UP
- **会刷新已拉过的**（Q1b），但**跳过 TTL 内的** —— 建议 10 分钟。
  否则连点两次 = 白跑一遍全部请求
- **节流**：每 `BULK_BATCH = 20` 个 UP 停一下（建议 2 秒）
- **可暂停 / 继续**（同一个 `shouldStop` 机制）
- **单个 UP 失败不中断整批**，结束后提示失败数量（`fetchHistoryForUps` 已有此能力）
- 进度实时更新 `已保存 N / M`

### 4.1 存储（数字已按实测修正）

⚠️ **修正**：我之前说"800 个 UP ≈ 1.73 MiB"是按**去掉 UP 名字和头像**算的。
但那会让**已取关的 UP**（`membership` 刻意保留）显示不出名字 —— 所以建议保留 `upName`/`upFace`：

| 方案 | 单元/张 | 每 UP（5 张） | UP 上限 | 总量 |
|---|---|---|---|---|
| 完整卡片 | 391 | 1,970 | 300 | 1.13 MiB |
| **只去 `upMid` + `url`（保留名字/头像）** | **~317** | ~1,600 | **600** | **~1.83 MiB** |
| 四个都去掉（已取关的会没名字） | 218 | 1,135 | 800 | 1.66 MiB |

**建议：只去 `upMid`（= key）和 `url`（可由 `bvid` 拼），保留 `upName`/`upFace`，`MAX_UPS = 600`。**
理由：`upMid` 是 key 本身、`url` 完全可推导 —— 这两个删掉是**纯收益**；
而名字/头像删掉会造成可感知的功能降级（已取关的 UP），不值得。

按此方案全量估算：upVideoCache 1.83 + feedCache 0.45 + followings 0.08 + read 0.09 ≈ **2.45 MiB**
→ Chrome (10 MiB) 25%、Firefox (5 MiB 量级) 49%。

### 4.2 必须拆 key（写放大）

现在 `saveUpVideos` 是"读出全部 → 改一条 → 写回全部"。缓存满时每次约 100ms 量级的
全量 `parse + stringify + setItem`，而 `fetchHistoryForUps` **每拉完一个 UP 就回调一次**
→ 拉 500 个 UP = 500 次全量序列化 ≈ **几十秒的主线程阻塞**。

**改为一个 UP 一个 key**：

```
bff:up:<mid>  =  { at, lastUsedAt, cards: [...5 条] }    // 每条约 1.6K 单元
```

- 写入变成 O(自己那 5 条)，小几百倍
- 淘汰用**前缀枚举** `bff:up:` 找 key，按 `lastUsedAt` 排序删除
- §3 的计数器只需**读 key 名**（解析出 mid），不用解析任何 value
- `bffUsage()` 仍能正确统计（它按 `bff:` 前缀求和）

### 4.3 淘汰判据改用 `lastUsedAt`

`at` 只在**发请求**时更新。而「多看一条」揭示缓存**不发请求** —— 于是在看的板块
反而可能因"很久没发请求"被挤掉。**揭示时也更新 `lastUsedAt`。**

## 5. 「多看一条」

- **纯本地，0 请求**。因为 `feed/space` 一页约 12 条，而每 UP 只留 5 条 → **一次请求就够 5 层**
- 每次点击：该板块层数 +1，显示上限随之提高
- 到第 5 层：按钮**禁用 + "已全部显示"**
- 揭示时更新相关 UP 的 `lastUsedAt`

⚠️ **依赖**：`feed/space` 一页必须 ≥ 5 条。早期实测约 12，安全 ——
但 `feed/all` 的条数我上次就记错过（记 21、实测 20），**建议开工前再探一次确认**。

## 6. 计数器与"被顶替"可见性

- 显示 `已保存 N / 共 M 个 UP`（N = 该板块 UP 中在缓存里有视频的数量）
- **全局淘汰导致某板块 N 下降时给一次提示**（Q5）：

```
「电影」板块有 UP 的缓存被挤掉了（缓存上限 600）
```

- **盲区说明**：淘汰是**全局**的（按 `lastUsedAt`），不看板块。
  在「游戏」板块拉取可能挤掉「电影」的 UP → 电影板块的计数会**无故下降**。
  提示正是为了解释这件事。
- **超大账号**：若分好组的 UP 总数超过 600，计数**永远到不了 M**。
  这时应显示"（缓存上限 600）"，而不是让用户以为是 bug。

## 7. Q1b「会刷新」的三个副作用（需要留意）

1. **请求预算变成"板块 UP 数"而不是"未覆盖数"** → 每次点击都是 M 个请求。
   缓解：TTL 跳过（§4）
2. **刷新会替换缓存数组** → 若某个 UP 发了新视频，层位置上移，
   用户正在看的"第 3 条"会变成另一个视频。这是刷新的应有行为，但要有心理预期
3. **模式 2 因此也能看到新视频** → 它不再只是"补齐历史"，也兼具刷新功能。
   好处是模式 2 更实用；代价是模式 1 / 模式 2 的职责边界变模糊

## 8. 请求与时间预算

单次「拉取更多」（M = 该板块 UP 数，间隔 400ms + 每 20 个停 2 秒）：

| M | 请求数 | 预估耗时 |
|---|---|---|
| 10 | 10 | ~6 秒 |
| 100 | 100 | ~70 秒 |
| 500 | 500 | ~6 分钟 |
| 5000 | 5000 | ~40+ 分钟 |

所以按钮上应显示"将请求 M 个 UP"，并保证**随时可暂停**。
