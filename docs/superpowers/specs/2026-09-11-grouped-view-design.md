# B站「只看关注」分组视图 — 设计文档

- **日期**：2026-09-11
- **状态**：设计已定稿，待用户审阅
- **关联**：
  - 前置设计：`docs/superpowers/specs/2026-09-11-bili-follow-feed-design.md`（热身版，已交付并验收）
  - 本设计是热身版之上的第二期功能
- **版本目标**：v0.3.0

---

## 1. 背景与目标

热身版（v0.2.0）已交付一个可用的「只看关注」页面：单一卡片墙，按发布时间/播放量排序，有已读标记。用户在真实使用后提出了分组化需求。

**目标**：把单一卡片墙升级为**按关注分组组织的多板块视图**，并提供侧边栏 UP 列表与本地分组管理。

## 2. 非目标（明确排除）

- ❌ **取消关注**（用户已决定不做）—— 本设计**不含任何写入 B站 账号的操作**，全部为只读接口 + 本地存储
- ❌ 不拉取 UP 的全量历史投稿（仍是动态流的"最近更新"）
- ❌ 不做定时抓取、不做跨设备同步（受用户脚本形态限制）
- ❌ 不做拖拽分类（先做菜单，拖拽留待以后，两者可共存）
- ❌ 不做分组排序以外的自动化（如按更新频率自动分组）

## 3. 需求（用户原话映射）

| # | 需求 | 本文档对应 |
|---|---|---|
| 1 | 按关注分组分板块展示，板块顶部有 `+`/`−` 折叠按钮 | §7.2 |
| 2 | 最左侧显示 UP 列表，按关注分组分类 | §7.1 |
| 3 | 卡片内 UP 名字/头像、侧边栏 UP 名字/头像加链接 → 跳 UP 个人主页 | §7.3 |
| 4 | 分组与 B站 **隔离**；可在我们页面对 UP 分类；**首次导入用 B站 分组初始化** | §5、§6 |
| 5 | 分类采用**菜单**方式，**支持批量处理** | §6.2 |

## 4. 数据模型

### 4.1 新增本地存储

| Key | 结构 | 增长特性 | 上限策略 |
|---|---|---|---|
| `bff:groups` | `Group[]` | 随分组数 | 用户自建，天然有界 |
| `bff:membership` | `Record<string, string[]>` | **随历史关注过的 UP 数**（取关后刻意保留） | 不设上限：单条约 38 字符，十年极端 churn 也仅 +126 KB |
| `bff:followingsCache` | `{ at, list: TrimmedFollowedUp[], tags }` | 随当前关注数 | 只存裁剪字段（见 §15.1） |
| `bff:biliSnapshot` | `Record<string, number[]>` | 随历史关注过的 UP 数 | 同 membership；可由「清理历史数据」批量清理 |
| `bff:schemaVersion` | `number` | 固定 | — |
| `bff:collapsedGroups` | `string[]` | 随分组数 | **侧边栏**分组的折叠状态，天然有界 |
| `bff:collapsedSections` | `string[]` | 随分组数 | **主视图**板块的折叠状态，与侧边栏**互相独立** |

> **实现时的一处简化**：原设计里的 `bff:upIndex` 已**取消**。侧边栏需要的名字与头像
> 直接由内存中的 `followingsCache.list` 计算得出（`buildUpIndex`），不额外落一份 ——
> 少一个派生缓存，就少一类"两份数据各自漂移"的 bug。

复用热身版已有的 `bff:readVideos`、`bff:lastVisitAt`。**其中 `bff:readVideos` 是唯一无上限增长项**，必须封顶 —— 见 §15.2。

### 4.2 类型

```ts
interface Group {
  id: string;                     // 'special' | 'uncategorized' | 'bili-<tagid>' | 'local-<n>'
  name: string;
  order: number;
  kind: 'system' | 'normal';
  source: 'bilibili' | 'local';   // 用于「重新导入」判断来源
}

interface UpInfo {
  mid: number;
  name: string;
  face: string;                   // 已提升为 https
  isSpecial: boolean;             // 来自 B站 special 或 tag 含 -10
}
```

### 4.3 两个系统分组

| id | 名称 | 行为 |
|---|---|---|
| `special` | 特别关注 | 置顶。**真实存储在 `membership` 里**，成员可增删 |
| `uncategorized` | 未分类 | **不写入 `membership`** —— `membership[mid]` 为空或不存在即视为未分类。始终存在，不可删除，排在最后 |

> 设计取舍：未分类用"隐式"表示（不落存储），避免出现"未分类"被当成真实分组而产生空分组噪音。

## 5. 首次导入与重新导入

### 5.1 首次导入（`membership` 为空时自动触发）

| B站 侧 | 本地侧 |
|---|---|
| `tagid=-10`「特别关注」 | 系统分组 `special` |
| `tagid=0`「默认分组」，即 UP 的 `tag === null` | 系统分组 `uncategorized`（即不写 membership） |
| 其他 `tagid` | 本地分组 `bili-<tagid>`，同名 |
| UP 的 `tag: [-10, 194111]` | 同时进 `special` 和 `bili-194111` |

**B站 的「默认分组」不建同名本地分组**，直接映射为「未分类」—— B站 该分组的语义就是"尚未分类"。

### 5.2 重新导入（合并，不覆盖）

> **只给本地尚未分类的 UP 按 B站 归类；已有本地归类的一律不动。**

这条是硬要求：否则用户在本地辛苦分的类会被 B站 的旧状态冲掉。UI 上提供两种入口：

- 「补充导入分组」—— 上述合并语义（默认，安全）。入口在**侧边栏底部**，显眼易找
- 「强制覆盖」—— 二次确认后完全按 B站 重建（逃生舱，供确实想重置时用）。入口在侧边栏顶部「⋯ 分组」菜单里，**刻意不放在显眼位置**，避免误点

#### 分组映射规则：按名字复用，不重复建同名组

把 B站 分组映射到本地分组时按此顺序匹配：

| 顺序 | 条件 | 动作 |
|---|---|---|
| 1 | `Group.biliTagId` 已等于该 tagid | 直接用它（之前导入过） |
| 2 | 存在**同名**的本地分组 | 视为同一个分组，把 tagid 记上去 |
| 3 | 都不满足 | 新建 `bili-<tagid>`，并记下 `biliTagId` |

**为什么必须有第 2 条**（实测踩到的 bug）：用户先在本地建了「娱乐」，之后在 B站 也建了「娱乐」并加了人。补充导入时因为 id 前缀不同（`local-1` vs `bili-386068xxx`）被判定成"本地没有"，于是新建了一个同名分组，UP 全进了新组 —— 出现两个「娱乐」。

根因是**只按 id 去重，没按名字去重**。修法是在 `Group` 上记 `biliTagId`，让 B站 分组到本地分组的映射成为**显式数据**，而不是靠 id 前缀猜。

**配套约束**：翻译 B站 归属时必须**查这张映射表**，不能靠拼 `bili-<tagid>` —— 复用同名分组后它的 id 是 `local-N`，拼出来的 id 指向不存在的分组，会产生脏引用让 UP 静默掉进「未分类」（一个比原 bug 更难发现的失败）。因此 `biliGroupIdsOf` 增加了可选的 `resolve` 参数。

**已知遗留**：本次修复只防新增，**不自动修复已经产生的同名重复分组**。清理方式见下方「用户操作」。

### 5.3 UP 增删的处理

每次拉取关注列表后，按下表处理：

| 情况 | 判定 | 处理 |
|---|---|---|
| **全新关注** | `membership` 与 `biliSnapshot` 均无该 mid | **自动按 B站 当前分组归类** |
| **重新关注** | 本地有历史记录 | **恢复原本地分类**，不吃 B站 |
| **已取关** | 不在当前关注列表 | 侧边栏隐藏；**`membership` / `biliSnapshot` 记录保留**，供日后重新关注时恢复 |

**为什么全新关注可以直接吃 B站 分组**：该 UP 在本地没有任何历史记录，不存在"覆盖用户劳动成果"的风险 —— 而"不覆盖本地分类"正是隔离方案唯一要守住的底线。全新的直接采用 B站 现成分类只有好处。

**为什么取关后保留记录**：单条约 63 字符（见 §15.5），重新关注时能免去重新分类。删掉没有收益。

### 5.4 分歧检测与单项重置

**问题**：B站 那边给某个 UP 换了分组，我们不会自动跟随（这是隔离的设计意图）。但**分歧是静默的** —— 用户会以为程序坏了。而且原设计只有「强制覆盖」一个出口，为同步一个人去重置全部显然不合理。

**做法**：记住上次导入时 B站 说了什么，才能区分"B站 变了"和"我自己在本地改的"。

```
bff:biliSnapshot   { [mid]: number[] }   ← 上次导入/重置时 B站 的 tagid 列表
```

- 每次刷新关注列表后，比较**当前 B站 tagids** 与**快照**
- 不一致 → 侧边栏该 UP 行显示 `↻` 标记
- 其「⋯」菜单多出一项「**按 B站 分组重置此项**」
- 重置后把该 mid 的快照更新为当前值，标记消失

> **为什么必须存快照**：若直接拿"B站 当前值"与"本地 membership"比较，**所有用户在本地手动改过的 UP 都会被误标成"B站 变了"** —— 而它们其实是用户自己的编辑。这个误报会让标记彻底失去意义。

**同步能力共五级**：

| 入口 | 范围 | 是否覆盖本地修改 |
|---|---|---|
| 补充导入分组 | 全部，但只碰**未分类**的 | 否 |
| **全部按 B站 对齐** | **只有检测到分歧的那些** | **是**（仅限分歧项） |
| 按 B站 重置此项 | 单个 UP | **是**（针对点的那一个） |
| **保持我的分类** | 只有检测到分歧的那些 | **否**（只推进快照，停止提示） |
| 强制覆盖 | 全部 | **是**（危险，藏在菜单里） |

> **「全部按 B站 对齐」补上了原先缺失的中间一级。** 实测反馈：用户看到 `↻` 标记后
> 不知道下一步该做什么 —— 逐个点 `⋯` 太累，强制覆盖又太重（会把**只属于本地**的
> 分类一起冲掉）。这个动作只碰有分歧的 UP，其余本地分类原样保留。
>
> **「保持我的分类」不是"隐藏提示"。** 它把快照推进到 B站 当前值，语义是
> "我看过了，决定保留自己的分类" —— 这些项因此自然不再被判定为分歧。
> 本地分类完好无损，且这是可复现的（不是只在本会话内隐藏）。
>
> **UI 配套**：侧边栏 UP 右侧的 `↻` 是**可点击**的，点它直接弹出该 UP 的分组菜单
> （原先只是个带 tooltip 的死标记，用户看不出该干什么）；只要存在分歧，主区顶部
> 会出现提示条，内含上面两个批量动作。

## 6. 本地分组管理与批量分类

### 6.1 分组 CRUD

| 操作 | 说明 |
|---|---|
| 新建分组 | 名称 ≤16 字符（与 B站 限制对齐，避免将来对不上）。id 为 `local-<递增>` |
| 重命名 | 同上长度限制；系统分组不可重命名 |
| 删除分组 | 二次确认；组内 UP 全部回落「未分类」，并在确认框里**明确告知数量** |
| 排序 | 分组菜单里的 `↑` / `↓`；`special` 恒在最前、`uncategorized` 恒在最后 |

### 6.2 单个 UP 分类（菜单方式）

侧边栏每个 UP 行右侧一个「⋯」按钮 → 弹出分组勾选框列表：

```
┌──────────────────────────────┐
│ 影视飓风           ↻ B站已变更 │
│ ☑ 特别关注                   │
│ ☐ 电影分组                   │
│ ☑ 技术分组                   │
│ ──────────────────────────── │
│ ＋ 新建分组…                 │
│ 移出全部分组（→未分类）       │
│ ↻ 按 B站 分组重置此项         │  ← 仅当检测到分歧时出现（§5.4）
└──────────────────────────────┘
```

勾选即生效（多选语义 = 追加/移除该分组），立即写本地存储。

### 6.3 批量分类

**进入方式**：侧边栏顶部「批量」按钮切换。开启后：

- 每个 UP 行左侧出现复选框
- 每个分组标题行出现「全选本组」复选框
- 底部出现操作条

```
已选 12 个   [加入分组 ▾]  [移出分组 ▾]  [仅属于… ▾]  [移出全部]  [清除选择]
```

**操作语义**：

| 操作 | 对选中 UP 的 `membership` 做什么 |
|---|---|
| 加入分组 G | 追加 G（保留其他归属，已存在则不变） |
| 移出分组 G | 移除 G；若移除后为空 → 自动落入未分类 |
| 仅属于 G | 直接替换为 `[G]` |
| 移出全部 | 清空 → 未分类 |

**约束与保护**：

1. 所有批量操作**只产生一次 localStorage 写入**（200 个 UP 也是瞬时）
2. 提供**撤销**：操作前留存 `membership` 快照，应用后显示「已应用 · 撤销」提示条（10 秒内有效）。批量误操作代价高，这个必须有
3. 批量操作**不影响 B站 账号**（本设计完全不写 B站）
4. 切换分组视图/平铺视图不退出批量模式，但刷新关注列表会退出并清空选择

## 7. 视图设计

### 7.1 侧边栏

```
┌──────────────────┐
│ [搜索 UP______]  │  ← 按名称过滤，跨分组
│ [批量] [⋯ 分组]  │
│ ──────────────── │
│ ▼ 特别关注 (5)   │  ← 分组标题可折叠
│   ☐ ● 山新   ⋯  │
│   ☐ ● Warma  ⋯  │
│ ▼ 电影分组 (8)   │
│   ☐ ● 影视飓风⋯ │
│ ▶ 技术分组 (12)  │
│ ──────────────── │
│ 刷新关注列表      │
│ 补充导入分组      │
│ 去 B站 管理分组 → │
└──────────────────┘
```

- 搜索时自动展开含匹配项的分组
- 侧边栏宽度固定（约 260px），可折叠以让出主区空间
- 「去 B站 管理分组 →」跳 `https://space.bilibili.com/<自己mid>/fans/follow`

### 7.2 主区分组板块

- 每个分组一个板块，标题为分组名 + 数量，左端 `+`/`−` 切换折叠
- **折叠状态存 `bff:collapsedGroups`**（key 为 groupId）
- **空分组默认折叠**并显示「这个分组最近没有更新」，否则 10 个分组会出现大量空框
- 板块内视频沿用热身版的卡片网格；组内排序与筛选沿用工具条的设置

### 7.3 卡片结构重构（必做）

第 3 条需求要求在 UP 头像/昵称上加链接。当前**整张卡片是指向视频的 `<a>`**，再嵌套就是 `<a>` 嵌 `<a>` —— 非法 HTML，浏览器会拆掉内层。

重构为**并列**结构：

```html
<div class="bff-card">
  <a class="bff-card-main" href="/video/BV...">   <!-- 封面 + 标题 -->
    <div class="bff-cover-wrap">…</div>
    <div class="bff-title">…</div>
  </a>
  <a class="bff-card-up" href="https://space.bilibili.com/{mid}">  <!-- 头像 + 昵称 -->
    <img class="bff-face"><span>UP 名</span>
  </a>
  <div class="bff-sub">播放量 · 相对时间</div>
</div>
```

侧边栏的 UP 行整体是 `<a href="https://space.bilibili.com/{mid}">`。

### 7.4 视图切换

工具条增加「分组 / 平铺」切换。**平铺视图完全保留**热身版行为（按 bvid 去重，不重复刷屏），作为快速浏览入口。

## 9. 纯函数与测试策略

沿用热身版做法：**逻辑尽量做成纯函数并 TDD，UI 靠人工验收清单**。

| 纯函数 | 测试要点 |
|---|---|
| `buildUpIndex` | `tag: null` → 未分类；`tag` 含 `-10` → isSpecial；face 的 `http://` 提升为 `https://` |
| `buildSections` | 多归属的 UP 视频出现在多个板块；分组顺序正确；空分组仍产出 Section；UP 不在索引中 → 未分类 |
| `localGroups` 的导入 | 首次导入映射正确；**合并导入不覆盖已有本地归类**；新关注的 UP 落入未分类 |
| 批量操作 | 加入/移出/仅属于/移出全部 四种语义；移出后为空自动落未分类；撤销能完整还原 |
| schema 迁移 | 旧结构（无版本号）能被安全读取或重置，不抛异常 |
| **存储上限与清理** | `readVideos` 超过 3000 条时丢弃最早的；`upIndex` 重建会移除已取关者；写入配额失败时返回失败而非静默吞掉 |

## 10. 边界情况

| # | 情况 | 处理 |
|---|---|---|
| 1 | 新关注的 UP | 自动落入「未分类」（§5.3） |
| 2 | B站 已取关的人 | 侧边栏不再显示；若其视频仍在动态流中，归入「未分类」 |
| 3 | 头像/封面是 `http://` | 复用热身版的 `toHttps`（否则 HTTPS 页面按混合内容拦截） |
| 4 | 本地分组名超长 | 限制 16 字符，与 B站 对齐 |
| 5 | 关注列表拉取失败（`-101` 未登录 / 风控） | 明确提示，侧边栏显示错误态；**分组视图降级为单一板块**而不是白屏 |
| 6 | `membership` 指向已删除的分组 | 视为未分类，读取时清理脏引用 |
| 7 | 删除分组时组内有 UP | 确认框显示数量，UP 回落未分类 |

## 11. Schema 版本与迁移

新增 4 个存储键，必须带版本号：

```ts
const SCHEMA_VERSION = 1;
// 读取时：若 bff:schemaVersion 缺失或不等于当前版本 → 走迁移或安全重置
```

**原则**：读坏数据时**降级到初始化状态并提示用户**，绝不抛异常导致白屏。这是热身版 `readState` 已经采用的策略，此处沿用。

## 12. 建造顺序

| 阶段 | 内容 | 风险 | 可交付成果 |
|---|---|---|---|
| **1** | 只读数据层：`relation.ts`、`upIndex.ts`、缓存 | 无 | 能拉到关注列表与分组 |
| **2** | 本地分组：`localGroups.ts`、首次导入、合并导入、批量语义、schema 版本 | 无 | 分类逻辑完备且有测试 |
| **3** | 视图层：侧边栏、分组板块、折叠、UP 链接、卡片重构、视图切换、批量 UI | 无 | 需求 1-5 全部落地 |

**三个阶段全部是只读接口 + 本地存储，不含任何写 B站 账号的操作。** 中途随时可以停下，不会有数据损失。

## 13. 已排除项

- **取消关注**：用户明确决定不做。因此本设计**不需要 `csrf`（`bili_jct`）**，也就**不需要那个 cookie 可读性探针**。整个第二期只用到 `GET x/relation/tags` 和 `GET x/relation/followings` 两个只读接口。

**探针时间**：2026-09-11，真实浏览器 + 真实账号（**281 关注 / 8 分组**）

### 对实现的三点影响

1. `biliGroupIdsOf` 里过滤 `tagid=0` 的防御性代码**保留** —— 它永不触发，但成本为零，且能抵御 B站 将来改变行为。

2. ⚠️ **未分类会成为最大的分组。** 该账号 281 个关注里 **262 个（93%）在默认分组**，即全部落入「未分类」：

   特别关注 0 / 求职 2 / 英语 2 / 学习 2 / 电影 1 / 游戏 10 / 日报 2 / 未分类 262

   - 主视图的「未分类」板块会占绝大部分内容。这是现状的真实反映、不是缺陷；自定义分组排在它前面，视觉上仍可用

## 15. 存储容量与清理

### 15.1 只存裁剪字段

容量估算的前提是**不把 B站 返回的完整对象直接落盘**。`x/relation/followings` 每项还包含 `sign`、`vip`、`official_verify`、`attribute`、`mtime` 等，体积是裁剪后的 **4-5 倍**。

落盘只保留：

```ts
interface TrimmedFollowedUp {
  mid: number;
  uname: string;
  face: string;            // 已提升为 https
  tag: number[] | null;    // B站 分组归属
  special: 0 | 1;
}
```

并且 **`face` 只在 `upIndex` 里存一份**，`followingsCache` 不再重复存头像 URL。

### 15.2 `readVideos` 必须封顶

`bff:readVideos` 是唯一**单调递增、没有天然上限**的键 —— 每点一个视频加一条，永不清理。

- 改为**数组存储**（保留插入顺序），不再用 Set 序列化
- **上限 3000 条**，超出时从最早的开始丢弃
- 依据：动态流能翻到的范围远小于 3000，更早的 bvid 不可能再出现在页面上，保留没有意义
- 估算：3000 × 17 字符 ≈ 50 KB，之后**固定在 50 KB 不再增长**

### 15.3 配额写满不再静默失败

热身版的 `saveRead` / `saveLastVisit` 目前是：

```ts
try { localStorage.setItem(...) } catch { /* 忽略 */ }
```

配额满、或用户在浏览器设置里禁用了网站数据时，这会**静默失败** —— 已读标记不再保存，而界面上毫无迹象，用户只会觉得"刷新后已读怎么又没了"。

**改为**：写入函数返回成功与否，失败时在界面上提示**一次**（不重复打扰）：「本地存储写入失败，已读状态可能不会被保存」。

### 15.4 存储占用可视化

在「⋯ 分组」菜单里显示一行：

```
存储占用：165 KB / 约 5 MB     [清理历史数据]
```

- 占用 = 所有 `bff:*` 键的 key + value 字符数之和
- 「清理历史数据」= 清空 `readVideos`，并清理 `membership` / `biliSnapshot` 中**已不在当前关注列表**的记录。二次确认，并显示将释放多少

### 15.5 容量估算（供参考）

| 场景 | 合计占用 | 占 5 MB 配额 |
|---|---|---|
| 关注 200 人 | ~165 KB | 3% |
| 关注 2000 人 | ~890 KB | 18% |
| 关注 2000 人 + 十年间取关过 2000 人 | ~1.0 MB | 20% |

**结论：关注/取关的 churn 不是风险。** 它只增加 `membership` 和 `biliSnapshot`（每条合计约 63 字符），且**不增加 `upIndex`**（该表只保留当前关注的人）。真正需要主动封顶的只有 `readVideos`。
